# Memex Phase 5.1 — Auth & Multi-user Implementation

This document explains the auth system added in Phase 5.1, which transforms Memex from a single-user app into a multi-user system with GitHub + Google OAuth.

---

## Architecture Overview

The auth system uses **Auth.js v5** (the official Next.js auth library, published as `next-auth@beta`) with a **Drizzle Adapter** to store sessions and accounts directly in your Postgres database. No external services needed.

```
User visits /login
         ↓
    Clicks "Sign in with GitHub"
         ↓
    Redirects to GitHub OAuth
         ↓
    GitHub redirects back with auth code
         ↓
    Auth.js exchanges code for tokens
         ↓
    Stores user, account, session in DB
         ↓
    User gets session cookie
         ↓
    Proxy checks cookie, allows access
         ↓
    API routes verify session, scope data by userId
```

## Schema Changes

### New Tables (Auth.js managed)

**`user`** — Core user profile
- `id` (text PK) — UUID generated by Auth.js
- `name`, `email`, `emailVerified`, `image`

**`account`** — OAuth account link (GitHub or Google)
- Composite PK: `(provider, providerAccountId)`
- Stores refresh tokens, access tokens, expiry
- Links to `user.id`

**`session`** — Active user sessions
- `sessionToken` (text PK)
- `userId` (FK) — which user owns this session
- `expires` — when this session expires

**`verificationToken`** — For email verification (not used yet, but required by Auth.js)
- Composite PK: `(identifier, token)`

### Modified Table

**`books`** — Added `user_id` column
- Foreign key to `user.id` with `ON DELETE CASCADE`
- All books now belong to exactly one user

## Key Files

### 1. `src/lib/auth.ts` — Auth.js Configuration

```typescript
export const { handlers, auth, signIn, signOut } = NextAuth({
  adapter: DrizzleAdapter(db, {
    usersTable: users,
    accountsTable: accounts,
    sessionsTable: sessions,
    verificationTokensTable: verificationTokens,
  }),
  providers: [GitHub, Google],
  pages: {
    signIn: "/login",
  },
  callbacks: {
    session({ session, user }) {
      session.user.id = user.id;  // Add userId to session object
      return session;
    },
  },
});
```

Key exports:
- `handlers` — `{ GET, POST }` for the `/api/auth/[...nextauth]` catch-all route
- `auth()` — async function to retrieve current session (used in Server Components & Route Handlers)
- `signIn()` / `signOut()` — Server Actions for auth flows

### 2. `src/app/api/auth/[...nextauth]/route.ts` — Catch-all Route

```typescript
import { handlers } from "@/lib/auth";
export const { GET, POST } = handlers;
```

This single file handles all OAuth flows:
- `GET /api/auth/signin` — redirects to provider
- `GET /api/auth/callback/github` — GitHub OAuth callback
- `GET /api/auth/callback/google` — Google OAuth callback
- `GET /api/auth/signout` — sign out
- `GET /api/auth/session` — retrieve current session (deprecated in favor of `auth()`)

### 3. `src/proxy.ts` — Auth Guard (Next.js 16)

In Next.js 16, the deprecated `middleware.ts` was replaced with `proxy.ts`:

```typescript
export function proxy(request: NextRequest) {
  const sessionCookie =
    request.cookies.get("authjs.session-token") ??
    request.cookies.get("__Secure-authjs.session-token");

  if (!sessionCookie) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!login|api|_next/static|_next/image|favicon\\.ico).*)"],
};
```

**What it does:**
- Checks for the Auth.js session cookie
- If absent, redirects to `/login`
- Excluded paths: `/login`, `/api/*` (API routes handle auth themselves), static assets

**Why not middleware.ts:**
According to Next.js 16 breaking changes, `middleware.ts` is deprecated. Use `proxy.ts` instead.

### 4. `src/app/login/page.tsx` — Login Page

Server component that:
- Redirects to `/` if already authenticated (via `auth()`)
- Shows two buttons: "Sign in with GitHub" and "Sign in with Google"
- Each button is a form that calls `signIn()` Server Action
- Dark zinc theme matching the main app

### 5. `src/components/NavBar.tsx` — Server Component Nav

```typescript
export default async function NavBar() {
  const session = await auth();
  if (!session?.user) return null;

  return (
    <nav>
      {/* Show user name/avatar */}
      {/* Sign out button that calls signOut() Server Action */}
    </nav>
  );
}
```

Rendered at the top of every page, shows logged-in user info and sign out link.

## Scoping Data by User

### Before: No auth
```typescript
// GET /api/books
const allBooks = await db.select().from(books);
```

### After: User-scoped queries
```typescript
// GET /api/books
const session = await auth();
if (!session?.user?.id) {
  return Response.json({ error: "Unauthorized" }, { status: 401 });
}

const userBooks = await db
  .select()
  .from(books)
  .where(eq(books.userId, session.user.id));
```

This pattern is applied to all three API routes:
1. `GET /api/books` — returns only the authenticated user's books
2. `GET /api/highlights` — joins with `books`, filters by `books.userId`
3. `GET /api/highlights/:id/connections` — verifies highlight ownership, limits results to user's other books

### Creating OAuth Apps

**GitHub:**
1. Go to GitHub Settings → Developer settings → OAuth Apps → New OAuth App
2. Set Authorization callback URL to `http://localhost:3000/api/auth/callback/github`
3. Copy Client ID and Client Secret into `.env.local`

**Google:**
1. Go to Google Cloud Console → Create a project
2. APIs & Services → Credentials → Create OAuth 2.0 Client ID (Web application)
3. Add redirect URI: `http://localhost:3000/api/auth/callback/google`
4. Copy Client ID and Client Secret into `.env.local`

## How Sessions Work

1. **User signs in** → OAuth provider verifies identity
2. **Auth.js creates:**
   - `user` row in DB
   - `account` row linking user to their OAuth provider
   - `session` row with a `sessionToken`
3. **Browser gets cookie** with `sessionToken` (httpOnly, Secure in prod)
4. **On next request:**
   - `proxy.ts` checks for session cookie
   - If present, request proceeds
   - If absent, redirect to `/login`
5. **In route handlers:**
   - Call `const session = await auth()`
   - `auth()` validates the session token and returns session object
   - Filter queries by `session.user.id`

---

## Security Notes

- **Session tokens** are stored in `httpOnly` cookies (can't be accessed by JavaScript)
- **OAuth secrets** are never exposed to the client (stored server-side only)
- **API routes** validate session on every request (no client-side auth bypass)
- **Proxy** is a first-line defense, but real auth happens in route handlers
- **Cascade delete** on `books` → deleting a user deletes all their books
